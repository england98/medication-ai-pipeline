# 이벤트 탐지 → VLM 검증 공동 개발 기준

## 1. 범위와 역할 분담

한 사람이 나오는 영상에서 **이벤트 탐지 → VLM 검증 → 세션 최종 판단**을 고도화한다. 인증·다중 인물 추적과 정식 세션 관리는 추후 별도 개발·통합한다.

| 담당 | 개발 범위 |
| --- | --- |
| **팀원: 이벤트 탐지·영상 처리** | 후보 탐지·종료, 전후 클립 생성, 프레임별 영역·관측 정보와 프레임 대응표 제공 |
| **사용자: VLM 검증** | 입력 프레임 선택, 같은 프레임의 영역 좌표로 ROI 생성, 리사이즈, 메타데이터 연결, 프롬프트 구성, 모델 실행·이벤트 판정 |
| **사용자: 통합·세션 판단** | 테스트용 세션·대상 정보 공급, 요청 조립·큐 연결, 이벤트 결과 종합·복약 완료 판단 |

**이번 기준은 ROI 이미지 생성을 VLM 측에서 담당하는 방식이다.** 현재 코드와의 차이는 4절에 정리한다. 이 문서를 검토한 뒤 기존 공동 개발 문서를 정리하고, 이후 변경 사항은 이 문서에 반영한다.

## 2. 후보별 전달물

| 전달물 | 내용 |
| --- | --- |
| **클립 MP4** | 이벤트 행동 전후 구간을 포함한 전체 화면 영상 |
| **`CandidateMedia`** | 클립 파일 위치, 요청·실제 확보 구간, `Clip.frames`의 클립 프레임 ↔ 원본 프레임·시각 대응표 |
| **`EventCandidate`** | 후보 ID·버전, E01/E02/E03 유형, 행동 시작·종료 시각, 관련 물체 ID |
| **`EventCandidate.regions`** | 대상자·손·입·물체의 bbox와 해당 원본 `FrameRef`. 후보 정보에 포함되는 목록 |
| **`DetectionInfo`** | 객체 클래스·점수·bbox·추적 ID, 손·입·포즈 랜드마크, 거리·접근 속도 등 움직임, 관측 가능 여부, 탐지 설정 참조 |

자료형의 기준은 [models.py](../shared/contracts/src/medication_contracts/models.py)다. JSON은 UTF-8로 전달하며, 세 객체는 **동일한 `context`와 후보 ID·유형·버전**을 가리켜야 한다.

팀원은 클립과 영역 **좌표**를 제공하고, ROI **이미지**는 VLM 측에서 만든다. 현재 계약을 유지할 때 팀원 산출물의 `Clip.rois`는 빈 목록 `[]`으로 전달할 수 있다.

```text
클립 + 후보·영역·관측·프레임 대응 정보
  → VLM 측 프레임 선택·ROI 생성
  → 전체 화면 이미지 + 같은 프레임의 ROI + 대응 메타데이터 + 프롬프트
  → VLM 응답 → 이벤트 판정 → 세션 최종 판단
```

모델에는 후보 공통 정보와 **선택한 프레임에 정확히 대응하는** 탐지 정보를 넣는다. 실제 입력 순서·출처·변환·프롬프트는 `ModelInputRecord`에 기록한다.

## 3. 팀원 질문에 대한 개발 기준

### ① 클립 코덱: MJPEG AVI도 가능한가?

- **MP4 컨테이너 + H.264 코덱**으로 전달한다. 현재 생성기는 `libx264`, `yuv444p`를 사용한다.
- 현재 VLM 로더는 MP4/MOV만 허용하므로 **MJPEG AVI 직접 입력은 지원하지 않는다.** 내부에서 AVI를 쓰면 전달 전에 MP4로 변환한다.
- 변환 후 실제 프레임 수·해상도·PTS와 `Clip.frames`가 일치해야 한다. 현재 PTS 허용 오차 기본값은 2ms다.
- 전달 형식의 샘플 클립 하나로 양쪽 디코딩을 먼저 확인한다.

클립은 행동 시작 전·종료 후 장면을 포함한다. 초기 전후 길이는 다음과 같으며 설정으로 조정할 수 있다.

| 후보 | 시작 전 | 종료 후 |
| --- | ---: | ---: |
| E01 준비·취급 | 1초 | 1초 |
| E02 입 전달 | 1.5초 | 1초 |
| E03 음수 | 1초 | 1초 |

EOF 등으로 영상이 부족하면 요청 구간과 실제 구간을 구분한다. 영상이 전혀 없으면 `clip=null`과 `unavailable_reason`을 전달한다.

### ② 전체 화면인가, 대상자 크롭인가? 회전·좌표 기준은?

- **대상자를 크롭하지 않은 전체 화면**을 전달한다.
- 회전이 필요하면 **탐지 전에 픽셀에 적용**하고, 회전 처리된 전체 화면을 탐지·클립 저장·좌표 계산의 공통 기준으로 삼는다. 미러링도 영상과 좌표에 동일하게 적용한다.
- bbox는 전체 화면 기준 `[x_min, y_min, x_max, y_max]`, 랜드마크는 `[x, y]`이며 값은 0~1로 정규화한다.
- `FrameRef.width/height`는 이 기준 화면의 실제 크기다. 내부 크롭·리사이즈 좌표는 전체 화면 좌표로 복원한다.
- `frame_index/source_ms`는 원본 스트림 기준, `session_ms`는 세션 기준이다. `clip_frame_index/clip_ms`는 클립 내부 기준으로 구분한다.

현재 코드에 명시적 회전 정규화 단계는 없으므로 회전 입력은 추가 구현·검증 대상이다.

### ③ 요청은 후보마다인가? 복약 1회당 최대 몇 건인가?

- **종료된 이벤트 후보마다 1건**이다. E01/E02/E03 단계별 고정 1건이 아니며, 반복 행동은 별도 후보로 여러 건 발생할 수 있다.
- 진행 중 revision마다 호출하지 않는다. 행동 종료 버전을 고정하고 후행 영상을 확보한 뒤 전달한다. EOF에서는 확보된 범위로 마감한다.
- 동일 요청의 재전달은 같은 `request_id`와 내용을 유지한다. 고정된 요청·후보 버전은 덮어쓰지 않는다.
- **복약 1회당 총 요청 건수의 고정 상한은 현재 없다.** 과도한 후보 분할은 탐지 측에서 조정한다.
- 현재 운영 기본값은 동시 추론 1개, worker 제출 한도 `max_pending=2`, 별도 대기 큐 한도 `max_queued=10000`이다. 복약당 건수나 실시간 처리량 보장은 아니다. 큐 초과 시 현재 코드는 요청을 보존하고 오류로 종료한다.

### ④ DetectionInfo.samples는 어느 프레임인가? 얼굴 점은 무엇이 필요한가?

**실제 탐지를 수행한 원본 프레임의 관측**을 기록한다. 해당 프레임이 클립에 포함되면 `sample.frame`·`region.frame`은 `Clip.frames[].source`와 정확히 일치해야 한다.

- 클립의 모든 프레임을 분석할 필요는 없다. 예: 20fps 클립 + 10fps 탐지 샘플.
- ROI가 필수인 실행에서는 VLM 측이 **유효한 영역 좌표가 있는 프레임 중에서 선택**한다. 다른 시점이 필요하면 추가 관측 절차가 필요하다.
- 영역이 부족할 때 입력 수 감소·추가 관측·실행 실패 중 어떤 정책을 쓸지는 VLM 측 설정으로 명시한다. 근처 프레임 좌표를 해당 프레임의 실측값으로 대체하지 않는다.
- 얼굴은 우선 현재 구현과 같은 **MediaPipe 점 13·14·61·291**을 `part="mouth"`로 제공하고 `MOUTH` bbox를 함께 전달한다. 얼굴 전체 점은 필수가 아니다.
- 손·포즈는 실제 관측된 점을 제공한다. 다른 모델을 쓰면 모델·버전·점 정의를 `detector_config`에 명시하고 대응을 합의한다.

관측했지만 검출 항목이 없으면 `OBSERVED`와 빈 목록, 관측 자체가 불가능하면 `UNAVAILABLE`과 빈 목록·사유를 기록한다. 이 상태는 현재 objects·landmarks·motions 묶음 단위다. 좌표·약 라벨·추적 ID를 임의로 채우지 않는다.

단일 대상의 `TARGET` 영역도 유지한다. 통합 담당자가 테스트용 대상 영역 공급을 연결하고, 탐지 측은 이를 후보 영역에 반영한다. 현재 검증기에는 클립 프레임과 연결되는 `TARGET` 영역이 필요하다.

### ⑤ 가루약을 컵에 넣는 MED_INTO_CUP은 어느 종류인가?

**E01 준비·취급으로 분류한다.** 컵에 넣는 것만으로 E02 입 전달·E03 음수·복약 완료를 판단하지 않는다.

현재 계약에는 `MED_INTO_CUP` 코드나 세부 행동 필드가 없다. 우선 E01 후보와 관측 근거를 전달한다. 별도 구분이 필요하면 subtype 등의 필드를 공동 계약에 정식 추가한다. 임의 JSON 필드 추가는 현재 스키마에서 허용되지 않는다.

가루약 복용의 완료 판단은 **약을 넣은 컵과 마신 컵의 연결, 투입 검증 질문, 완료 규칙**을 추가해야 한다. 기존 E01 질문은 취급·내용물 꺼냄을 확인하며 컵 투입을 전용으로 검증하지 않는다. 현재 E01+E03만으로 가루약 복용 완료를 확정할 수 없다.

### ⑥ 파일 큐인가? locator는 무엇이며 요청은 누가 만드는가?

**공유한 D13의 파일 큐 방식으로 연결하고, `VerificationRequest`는 사용자 담당 통합 코드에서 만든다.**

1. 팀원이 MP4와 `EventCandidate`·`DetectionInfo`·`CandidateMedia`, 탐지 설정 파일을 완성한다.
2. 통합 코드가 연결을 확인하고 요청 ID·모델·프롬프트·실행 설정을 붙인다.
3. `VerificationRequest`와 테스트 `SessionContext`를 큐에 저장한다.
4. VLM 측이 처리하고 결과를 통합·세션 판단 측으로 전달한다.

현재 큐 파일은 `queue/<request_id의 SHA-256>.json`이며 `{"request": ..., "session": ...}` 구조다. runtime이 관리하는 파일 기반 큐이며, 외부 프로세스의 파일 투입을 자동 감시하는 기능까지 구현된 것은 아니다. 인계·등록은 통합 코드가 연결한다.

`ResourceRef.locator`는 **실제 파일을 읽을 수 있는 위치**다.

| 참조 | 파일 |
| --- | --- |
| `clip.video.locator` | 클립 MP4 |
| `detector_config.locator` | 탐지 모델·임계값·관측 정의 등 설정 |
| `execution_config.locator` | VLM 실행 설정 |

- 현재 미디어 로더는 로컬 경로·로컬 `file:` URI를 지원한다. HTTP·S3 다운로드는 지원하지 않는다.
- 공유 자료는 **합의한 자료 루트 기준 상대 경로**를 권장한다. 예: `media/clips/<clip_id>/video.mp4`. 수신 측에서도 동일 구조의 실제 파일에 접근할 수 있어야 한다.
- 상대 경로 기준은 통합 코드에서 지정한다. 현재 VLM CLI는 요청 JSON의 부모 폴더, 전체 runtime은 실행 폴더를 미디어 루트로 사용하므로 실행 경로에 맞춰 설정한다.
- 파일 쓰기가 끝난 뒤 요청을 공개한다. 처리·재시도·공동 검토 중에는 참조 파일을 삭제·덮어쓰지 않는다.

### ⑦ 세션·인증·완료 담당과 ‘안 먹음·불확실’ 기록은?

통합·VLM 검증·세션 최종 판단은 사용자가 담당한다. 인증·추적과 정식 세션 관리는 추후 별도 통합하며, 이번에는 통합 코드가 테스트용 식별자·문맥을 공급한다.

| 구분 | 현재 기록 | 의미 |
| --- | --- | --- |
| 이벤트 확인 | `VerificationResult.verification=CONFIRMED` | 해당 이벤트 확인 |
| 이벤트 반증 | `verification=REFUTED` | 해당 후보에 대한 반증 |
| 이벤트 불확실 | `verification=UNCERTAIN` | 정상 처리했으나 영상 근거가 불충분 |
| 오류·미실행 | `processing_status=ERROR / NOT_RUN`, `error` | 실행 문제. `verification=null` |
| 세션 완료 | `CompletionRecord.session_result=COMPLETE` | 세션 완료 규칙 충족 |

후보별 결과는 `verification/*/result.json`, 실제 입력은 `model_input.json`에 기록한다. 세션 판단 측은 수신 결과·평가 이력과 완료 기록을 보존한다.

**후보 하나의 REFUTED는 세션 전체의 ‘안 먹음’이 아니다.** 후보 없음·불확실·EOF·실행 오류도 자동으로 미복약 판정이 되지 않는다. 현재 세션 자료형은 COMPLETE 또는 미확정(null)만 지원한다. 세션 단위 ‘미복약·불확실’ 최종값은 관찰 종료 기준·판정 정책·자료형을 사용자 측에서 별도로 확장한다.

현재 완료 판단은 약 식별·입 전달이 확인된 E02, 대상 일치, 관련 근거의 상충 여부를 중심으로 하며 E01/E03는 보조 근거다.

## 4. 현재 코드에서 변경할 사항

| 항목 | 이번 개발에서 할 일 |
| --- | --- |
| ROI 생성 위치 | 영상 처리의 사전 ROI 생성 책임을 VLM 입력 준비 단계로 이동 |
| 프레임·ROI 연결 | 선택한 전체 화면 프레임의 좌표로 ROI 생성. 기존 `include_rois=true`만으로는 이 방식이 구현되지 않음 |
| ROI 입력 기록·검증 | 새로 생성한 ROI의 원본 프레임·bbox·이미지 참조·변환 기록을 남기고 검증 로직도 수정. 현재 검증기는 요청의 `Clip.rois`를 참조하므로 함께 변경 필요 |
| 회전 입력 | 탐지·저장 영상·좌표의 방향을 통일하는 단계 구현·검증 |
| 가루약·세션 결과 확장 | 전용 subtype·질문·완료 경로, 미복약·불확실 최종값이 필요할 때 계약과 규칙을 함께 변경 |

입력 프레임 수·선택 방식·ROI 결합 방식·여백·해상도는 VLM 측에서 설정한다. 과거 테스트의 전체 화면 4장·ROI 사전 생성 8장은 이번 전달 계약의 고정 수량이 아니다.

## 5. 첫 공동 실행에서 확인할 것
